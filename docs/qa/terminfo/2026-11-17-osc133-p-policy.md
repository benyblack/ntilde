## Primary semantics and implementation decision

The [Contour OSC 133 specification](https://contour-terminal.org/vt-extensions/osc-133-shell-integration/#p-prompt-part-start)
defines `P` as the start of a further part of an existing prompt, using `k` to identify
the kind. Its right-prompt form is `P;k=r`, and it starts no new command block. This is
not a cwd setter. The [VS Code specification](https://code.visualstudio.com/docs/terminal/shell-integration#_supported-escape-sequences)
documents `P;<Property>=<Value>` and `Cwd` in its **OSC 633** dialect; its OSC 133 section
documents A/B/C/D. Both sources were read on 2026-11-17. The linked semantic-prompts
proposal on freedesktop GitLab was access-challenged; it is not claimed independently
verified here. The Contour specification is the primary source used for prompt-part
semantics, rather than a secondary summary or the benchmark's feature label.

No source-backed cwd effect contract was found for the exact `133;P;Cwd=/tmp` fixture.
It must not be silently interpreted as OSC 633 P, OSC 7 or a different lifecycle mark.
The current `AnsiParser.ShellIntegration.cs` dispatches only A/B/C/D and ignores P.
There is no prompt-kind/boundary state or independent boundary observation in the App's
pane metadata API. The decision is to retain the unsupported P forms and defer prompt-part
implementation/qualification. This is an implementation policy, not a newly measured
unsupported benchmark grade. Absence of a suitable observer is not proof of terminal failure.

Before qualifying prompt parts, specify the boundary/kind coordinates and lifetime,
valid distinguishable primary/right/continuation controls, behavior across prompt redraw,
screen switches and resize, independent host readback, and exact restoration. Keep command
anchors, readiness, cwd and cells as separate facts. Only then can a new measured effect
contract decide support or failure. This audit adds no such contract and no production API.
